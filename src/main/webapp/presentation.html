🚨 The Problem

Traditional Perimeter Security is Dead

  • Cloud adoption dissolves network boundaries
  • Remote work expands attack surface
  • Lateral movement after breach is common
  • Single authentication at entry is insufficient

Real-World Impact

A healthcare breach exposed 5M+ patient records because attackers moved laterally after initial access. Traditional "castle-and-moat" security failed.

🎯 Zero Trust Principles

Never Trust

  • No implicit trust
  • Every request validated
  • Location doesn't matter

Always Verify

  • Continuous validation
  • Context-aware decisions
  • Least privilege access

Core Tenets

  1. Verify explicitly - Always authenticate and authorize
  2. Least privilege - Limit access with just-in-time/just-enough
  3. Assume breach - Minimize blast radius and segment access

✅ Input Validation: Zero Trust for Data

Never Trust Input, Always Verify


public record Patient(
    String id,
    @NotBlank(message = "First name is required")
    @Size(min = 2, max = 50)
    String firstName,

    @NotNull
    @Past(message = "Date of birth must be in the past")
    LocalDate dateOfBirth,

    @Pattern(regexp = "\\d{3}-\\d{2}-\\d{4}")
    String ssn,

    @Email String email,
    @Pattern(regexp = "A\\+|A-|B\\+|B-|AB\\+|AB-|O\\+|O-")
    String bloodType
) {}

🔐 Validation as Zero Trust Control

Before (Trusting)


public Response create(
    Patient patient) {
  // DANGEROUS
  // Accepts anything
  return save(patient);
}

After (Zero Trust)


public Response create(
    @Valid @NotNull
    Patient patient) {
  // SAFE
  // Validated first
  return save(patient);
}

Automatic Validation

Jakarta EE validates before method execution. Returns HTTP 400 if invalid.

No manual null checks needed!

🚫 Attack Prevention via Validation

Constraint Attack Prevented Example
@Pattern SQL Injection, XSS SSN format enforcement
@Size Buffer Overflow, DoS Max 1000 chars
@Past Logic Bypass Date of birth check
@Email Format Attacks Email validation

Immutability with Records

Records prevent post-validation tampering - Data can't be modified after validation

🎓 Key Takeaways

  1. Zero Trust is not optional - Modern threats require continuous verification
  2. Jakarta EE 11 provides the foundation - Security APIs, CDI, interceptors
  3. Validation is security - Input validation prevents attacks at the boundary
  4. Immutability matters - Records prevent post-validation tampering
  5. Fine-grained authorization matters - Roles alone are insufficient
  6. Monitoring is part of security - Observability enables detection and response
  7. Performance doesn't suffer - Well-designed security adds minimal overhead

Start Small, Scale Smart

Begin with authentication and validation. Add ABAC and monitoring incrementally.

✅ Implementation Checklist

1. Authentication Layer

  • Implement custom HttpAuthenticationMechanism
  • Integrate with OIDC provider (Keycloak, Auth0, Okta)
  • Validate JWT signatures and claims

2. Input Validation Layer

  • Add Bean Validation constraints to models
  • Use @Valid on API parameters
  • Convert to immutable records where possible

3. Authorization Layer

  • Create custom security annotations
  • Build CDI interceptors for ABAC logic

4. Monitoring Layer

  • Implement CDI event observers
  • Add MicroProfile Metrics
